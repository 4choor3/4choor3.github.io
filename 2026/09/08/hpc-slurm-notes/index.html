原创折腾 HPC SLURM Linux

学校 HPC 集群

陈鑫宇2026-09-092026-09-16

这是学校的高性能计算平台，机器两百多台，交给 SLURM 调度的是其中 171 台——一万两千多个 CPU 核，内存按调度器口径加起来九十多 TB，外带一个 23PB 的并行文件系统。

机器不是一批买齐的，代际混着用。

占大头的一百二十台是早年的 CPU 节点，双路 32 核的 Xeon 8358P，单机 64 核配 500G 内存，日常计算量基本都吃在这批机器上。

中间补了几台胖节点，四路 24 核的 Xeon 8360H，单机 96 核 2T 内存，留给吃内存的活。

最新的那批跑 GPU，单机 96 核配 1T 内存、插了八张 H20，另有一台装两块 4090。

还有两台国产 K100 的异构节点，五月末就挂着没起来。

平台另有二十多台 GPU 机器未纳入 SLURM 节点列表；登录、管理、监控这几类机器同样不计入调度器口径，sinfo 不显示。

平台的主要用户是做生信和计算化学的，module avail 里八十七个模块，blast、bwa、vasp、gromacs 占了大半。我拿它跑 A 股量化和模型推理。

登录节点只管登录，跑代码得去计算节点。这个平台走 SLURM 23.11.10，下面这些是登录进去一条条敲出来的。

分区怎么选

分区 节点数 CPU 型号 单机核数 单机内存 加速卡
cpu64（默认） 120 Xeon Platinum 8358P 64 500G —
cpu96 5 Xeon Platinum 8360H 96 2T —
test96 2 Xeon Platinum 8558P 96 250G —
soy-com 22 Xeon Platinum 8558P 96 500G —
sri-com 14 — 96 500G —
sri-mem 2 — 96 2T —
sri-ghz 2 — 32 500G —
sri-gpu 1 — 96 1T H20 × 8
sri-gnm 1 — 96 500G 4090 × 2
dcu 2 — 48 250G 国产 K100 × 2

十个分区加起来 171 台、12352 核。cpu64 里 118 台是 500G 内存，另外两台 384G。

sri-* 这一组绑定着专属 QoS，普通账号提交报 Invalid qos specification，型号取不到；dcu 两台离线，同样取不到。

cpu64 的 120 台是主力：空闲 95 台时可直接提交；25 台在跑时，backfill 仍能插入空闲窗口。内存账面上记 500G，进节点 free -g 看是 503。

DCU 那两台装的是国产 K100，sinfo 里是 down*，scontrol show node 给出的原因是 Not responding，从五月底一直挂到现在。带加速卡的另外两台——sri-gpu 的 H20 和 sri-gnm 的 4090——就在上面那组用不了的 QoS 里面。

有个容易忽略的区别：老的 CPU 节点是 CentOS 8.2、内核 4.18，后加的 GPU 和内存节点已经是 RHEL 9.5、内核 5.14。看 /hpc/software 里 gcc 从 4.8.5 一路装到 14.1.0、glibc 备了 2.29 和 2.36 两套，对应两代系统各自保留一版。自行编译的二进制跨分区搬运存在兼容问题。

正式任务写脚本交给 sbatch：

申请加速卡加一行 #SBATCH --gres=gpu:1，具体型号看分区里的 Gres 字段。

这个集群的 SelectTypeParameters 是 CR_CORE，调度只按核数分，内存不进资源分配——作业不写 --mem 照样跑，节点上的 AllocMem 一直是 0。我拿两个 1 核作业试过，运行期间所在节点的 AllocMem 都是 0。同一节点上的多个作业互相不可见对方的实际内存占用，先吃满内存的作业会影响其他作业，因此提交时显式指定 --mem。sacct 里 ReqMem 那栏显示 500000M，是没填这个字段时默认拿节点总内存来显示，不是真申请了整台机器。

数组作业上限 MaxArraySize 为 1001，单次最多提交 1001 个子任务，批量任务需分几批提交。

调度器按什么排

PriorityType = priority/multifactor，SchedulerType = sched/backfill。前一个按作业年龄、份额、队列权重算优先级，后一个负责插空——只要你的作业能在某个空闲窗口跑完，就允许提前启动。

这组合对短作业友好，反过来也一样：给一个 5 分钟的任务写 --time=72:00:00，backfill 找不到足够长的窗口，作业只能等待。

所有分区的时间上限都是 infinite，MaxTime 那栏没有任何限制，这个上限实际交到使用者手里，长时间占用的作业会持续占用节点。

squeue -a 在普通账号下不显示其他用户的作业：实测 squeue -a -h | wc -l 返回 0，同一时刻 sinfo 显示 25 个节点处于 alloc 状态。判断集群负载只能看 sinfo 的节点状态分布。

存储：23P 与 5000 亿 inode

df -hT 里最显眼的一行：

23PB 的并行文件系统，用了 1.1PB。文件系统类型那栏写的是 dpc，属于分布式存储客户端挂载，跟本地盘完全不是一回事——小文件随机读的性能和顺序读写差着量级，这也是登录节点上禁用 du / find 的由来。

inode 也得看：df -i /hpc 是 5000 亿个，用掉 2.33 亿。数字这么大，是因为元数据按目录树铺开、查询要走网络。

另外两个挂载点：

  • /usr/local/globle/softs 是 NFS，191G、59% 已用，放的是 slurm 二进制和公共软件，所有节点共享同一份。
  • /dev/shm 给了 252G 内存盘。数据管道的中间结果我放这儿，读写不落盘；重启即清空。

家目录在 /hpc/home/<用户名>。我那份快 48TB，大头是 49 个从 ModelScope 拉的模型，剩下是量化的日线数据。

环境与启动速度

公共软件走 module，module avail 里挂了 87 个。生信那一堆（blast、bwa、hmmer、canu、megahit、gtdbtk、metawrap）、计算化学那几个（vasp、gromacs、amber、autodock）、gcc/4.8.5 到 gcc/14.1.0、openmpi 3.1 到 5.0.5、cuda/11.7 和 12.4、Python 3.7/3.8、R 三个版本、singularity 两个版本。用之前 module load gcc/14.1.0 openmpi/5.0.5 就行，比在 home 里自己编译省事。

Python 我走 miniconda，四个环境分开：myenv 放通用工具，quant 放 baostock 那套，agent 和 agent-gpu 分开是因为 GPU 那边的依赖锁在另一个 cuda 版本上。

zsh 的启动时间专门优化过。原来要 15 秒，因为 oh-my-zsh 加几个插件每次登录都重新 source，而 home 挂在分布式存储上，网络文件系统的随机读本来就慢。做法是把 omz 和历史文件缓存到 /dev/shm，再把”重新加载配置”写成一个函数跳过 omz 的重复加载。现在 0.8 秒上下，多个终端窗口同时打开时差异明显。
