把 711MB 课程资料塞进 Git

陈鑫宇2026-10-042026-10-04

课程资料一直在 OneDrive 里。上学期末改一份植物学复习提纲，存完第二天想找前一版，已经没了。OneDrive 只留当前状态，改坏了就是改坏了。

两台电脑同时开着同一个 docx 更麻烦。同步回来多出一个名字带 (2) 的副本，哪个是新的得自己判断。

我想要的只是能回到上周三那一版。所以整个目录交给了 Git。私有仓库，564 个文件，711.1 MiB，12 个提交。

同步方式很粗：OneDrive 那边有改动，就整目录覆盖提交一次，不做挑选，commit message 直接写课程名，比如 生物化学PPT。改之前先 git pull --rebase，不然远端 README 动过就会撞上。

.git 里的 670MB

整个目录在磁盘上 1.3G，工作树七百多兆，.git 六百七十兆，差不多两份。count-objects 报 673 个对象、670.32 MiB，packs: 0 —— 从建好到现在一次都没打包过，全是散对象。

其中 561 个是 blob，原始内容加起来 821.1 MiB，落盘 670 MiB，zlib 只吃掉 18%。压不动是预期内的，mp4、jpg、pdf 内部本来就是压缩流，再过一遍没什么可榨的。delta 对二进制也指望不上，jpg 改一个像素就是个全新 blob。

还有十来个路径内容重复，同一份课件在两个目录各存了一遍。Git 按内容存，只算一份。

README 里我写过「历史中含一次 300 文件重命名，对象库因此偏大」。这句是错的，回头查了一遍。

77ce40a 更改文件夹顺序 那次，git show --diff-filter=R 数出来 562 个重命名，全是 R100。R100 的意思是内容一模一样，而 Git 按内容算 hash，内容不变就是同一个 blob，重命名一个字节都不会多写。多出来的只有 99 个 tree，加一起 35KB。

562 也不是 300。300 是我当时随手估的，没数。

那次重排干了三件事：去掉 文档/我的文档/ 两级前缀、大一 改 大一上、大一 (2) 改 大一 下。动机很实际，路径太长，我在 README 里列索引的时候每行都要拖一串前缀。

代价是 README 里所有路径当场作废。第二天 7936451 整条提交就是用来把 README 同步到新结构的。前一次提交动了 566 个文件，562 个是纯重命名，真有改动的只有 4 个。再往前一点 17f6dd0 是一次 merge：我在本地挪目录的同一时间远端 README 也动过，ort 策略给合了。

那 110MB 的来历

按 hash 对了一遍，561 个 blob 里有 8 个不在当前 HEAD 上，一共 113.5 MiB。其中一个 115,343,360 字节。

reflog 里能找到它的来历：

test-big.bin 是我拿来试大文件拦截规则的。规则生效了，提交也进去了，然后我 reset 回 HEAD~1 把它丢了。提交没了，blob 还在 —— reflog 还指着那个提交，gc 不敢动它。

所以那 670MB 里，一百一十来兆是我自己测试剩下的垃圾，剩下五百五十多兆是一份完整快照，跑不掉。

清掉就是两条命令，reflog expire 跟一句 gc --prune=now。

.gitattributes 不存在，git lfs 在这台机器上直接报 not a git command，从来没装过。后来也没装：LFS 管的是「同一个大文件反复改，别每版都存一份」，这批资料进去之后基本不动，12 个提交里大部分是在改 README 和做测试。真要上 LFS 也行，只是已经在历史里的几个 mp4 得用 git filter-repo 重写成指针。

按扩展名拆一遍，数量和体积完全不成比例：

类型 个数 体积
mp4 3 193.8 MiB
pdf 74 184.0 MiB
ppt / pptx 34 107.7 MiB
docx 63 98.8 MiB
doc 30 52.0 MiB
jpg 317 66.2 MiB
md 14 0.2 MiB

md 只有 14 份，0.2 MiB，是整个仓库里唯一能 diff、能在 GitHub 上直接渲染的东西，动物学和有机化学的复习笔记都在里面。剩下七百多兆改了什么，git 只能告诉我「二进制文件有差异」。

jpg 三百多个却只占 66.2 MiB，都是植物学那批标本照片。

ppt 和 pptx 没转 pdf —— 转成 pdf 就把动画和备注丢了，复习的时候这两样都要用。

不该进的是 mp4 和 zip。3 个视频吃掉 193.8 MiB，占总量 27%，还是全仓库里离 GitHub 上限最近的东西，大一上/学科导论/output.mp4 单个 94.4 MiB，离 100MB 硬限只剩 5.6MB。提交脚本里我跳过大于 50MB 的文件，比 LFS 糙。

OneDrive 留下来的

路径前面那两级 文档/我的文档/ 是 Windows 那套，整个跟着目录一起过来了。

大一 (2) 是 OneDrive 冲突副本的命名习惯，被我改成了 大一 下。这样的 (2) 后缀库里一共 7 个，全是当年两台机器同时开着同一份文件时留下的，至于是不是都还需要，我到现在没逐个看过。有个文件名里带英文双引号，5158fe5 修复引号 那次专门把引号去掉 —— macOS 允许，" 在 Windows 上是保留字符，同步过去就要出问题。

.gitignore 第一行就是 ~$*，但仓库里还留着 6 个 ~$xxx.docx 锁文件。规则只对未跟踪文件有效，这 6 个在第一次整目录提交时就进去了。

仓库本身放在 OneDrive 同步目录之外，.git 不会被同步上去。六百七十多个散对象让 OneDrive 去盯，光文件数就够它呛的。

core.ignorecase 和 core.precomposeunicode 都是 init 时按 APFS 自动写进去的 true。前一个意味着只改大小写的重命名 Git 看不见；后一个是 macOS 的 NFD 归一化，换到 Linux 上 clone 中文文件名可能对不上。目前没撞上。
