1. 服务器基线确认

1.1 前置条件

已从算力平台获得：IP、SSH端口、root密码、已选镜像（PyTorch 2.1.2 / Python 3.10 / CUDA 12.1）。

1.2 登录与系统确认

可验证结果：

提示符(py310)说明conda已自动激活预置环境py310，路径在/usr/local/miniconda3/envs/py310。这一步决定了后续第2节的坑。

1.3 GPU与驱动确认

可验证结果：nvidia-smi输出中Memory-Usage初始接近0 MiB；训练开始后应稳定在 16~21 GB区间，Volatile GPU-Util维持90~100%。低于50%说明数据加载或 batch配置存在瓶颈。

1.4 磁盘确认

7B模型会产出三份大文件：基座缓存（~15GB）+ 合并模型（~15GB）+ GGUF（4~8GB）。系统盘放不下时必须切数据盘（AutoDL为/root/autodl-tmp）。

2. 安装LLaMA-Factory

2.1 操作目的

获得训练 / 合并导出 / 格式转换的统一入口llamafactory-cli。

2.2 报错 1：Python版本不满足

触发命令：pip install -e .[metrics]（在默认py310环境中）

错误原文：

排查定位：报错直指llamafactory==0.9.6.dev0的元数据约束。从同一段日志可看到该版本的依赖收敛范围：

即：0.9.6.dev0强制Python ≥ 3.11，与镜像预置的3.10.16冲突。选型阶段推荐的「Python 3.10依赖冲突最少」在此版本上已失效。

解决过程：新建conda环境后重装。

可验证结果：

实测装到的关键版本：torch 2.14.1、transformers 5.8.0、peft 0.18.1、trl 0.24.0、accelerate 1.11.0、gradio 5.50.0、modelscope 1.40.2。

版本号核验（重要）：日志中的llamafactory==0.9.6.dev0不是发布版本。核验结果：

PyPI与GitHub tag最新均为 v0.9.5，不存在0.9.6。0.9.6.dev0是pip install -e .从master源码安装时，setuptools_scm基于最新tag自动推断出的开发态版本号（即v0.9.5之后的未发布快照）。

影响：凡本文引用src/llamafactory/...源码作为依据处，均指master分支当前代码，与v0.9.5正式版可能存在差异；与0.9.6.dev0快照的差异未做逐commit比对。

结论：镜像选择应直接选Python 3.11，可省掉这一轮重建。CUDA版本仍选12.1（预编译wheel的最大公约数，避免云端源码编译）。

4.2 报错 3/4/5：三次CUDA OOM

# cutoff_len batch size grad_accum gradient_checkpointing 结果

3 2048 2 16 是 Step 9仍OOM

错误原文（第 1 次）：

第 2、3 次报错同构，仅数字变化：Tried to allocate 2.32 GiB ... of which 2.08 GiB is free ... this process has 21.04 GiB memory in use。

排查定位：

  • 崩溃点固定在transformers/loss/loss_utils.py:37 fixed_cross_entropy→torch._C._nn.cross_entropy_loss，即反向传播起点，不是前向；
    -18.82 GiB is allocated by PyTorch说明基座权重 + 激活值已吃满，剩余2.20 GiB不够分配logits的梯度（batch×seq×152064词表）；
  • 关键：第3次已开gradient_checkpointing仍崩 → 说明单样本峰值由最长序列决定，而数据中存在5,313字符的样本。cutoff_len 2048下该样本的 logits 张量本身就是显存炸弹。

解决过程：把cutoff_len从2048降到1024、batch降到1、梯度累积升到32保持等效batch size不变。

6. 量化：四条路径的实测结果

路径结论汇总（先看结果）

路径 做法 结果 判定
A LLaMA-Factory Export页选量化等级 下拉框置灰，未产出 ❌ 该选项是 GPTQ位数量化（2/3/4/8），不是GGUF；置灰原因是多选了checkpoint
B convert_hf_to_gguf.py --outtype q4_k_m 三个报错连环，未产出 ❌--outtype根本不支持K-quant
C 独立 venv +convert_hf_to_gguf.py --outtype f16→llama-quantize Q4_K_M 未在本文环境跑完 ✅ 唯一可行，官方two-phase流程
D ollama create -f Modelfile导入 safetensors 可运行 ⚠️ 可用于验证推理效果，但Ollama导入时不量化

唯一可达成目标的路径是C。 B的失败见6.2，C的完整做法见6.3，D的定位见6.4。

6.1 路径A：LLaMA-Factory直接导出GGUF —— 失败

操作：Export页面选择「导出量化等级」，或命令行--export_quantization_bit。

现象：WebUI中「导出量化等级」下拉框置灰不可选；命令行方式同样未产出GGUF。

源码级排查（克隆hiyouga/LLaMA-Factorymain分支，src/llamafactory/webui/components/export.py）：

置灰根因（已定位，非"环境缺组件"）：当checkpoint_path是非空 list（即在检查点选择框里选了多个checkpoint目录）时，can_quantize()直接返回interactive=False。与llama.cpp组件、GGUF依赖无关。

该选项的真实语义（已定位，不是GGUF）：

结论：

  1. 「导出量化等级」= GPTQ位数量化（2/3/4/8 bit），依赖optimum+gptqmodel，产出的是 GPTQ量化的safetensors模型，与GGUF的q4_k_m是两条完全不同的技术路线；
  2. 置灰触发条件是多选了checkpoint，不是环境缺组件；
  3. GPTQ路线还要求必填校准数据集（__post_init__中export_quantization_dataset is None直接raise ValueError），且GPTQ + LoRA adapter组合被WebUI显式禁止（err_gptq_lora）；
  4. LLaMA-Factory README（main）全文无GGUF/llama.cpp/--export_quantization关键词，GGUF导出无官方文档依据。

判定：LLaMA-Factory 无法产出q4_k_m GGUF，不作为量化路径。

6.3 路径C：独立venv + 官方两步法（唯一可行路径）

依据：llama.cpptools/quantize/README.md原文 —— 「Quantization is done in two phases: Convert the original model to GGUF format. Quantize the converted GGUF file.」

关键事实（源码级核验，convert_hf_to_gguf.pyargparse定义）：

--outtype不接受任何K-quant类型（无 q2_k / q3_k / q4_k_m / q5_k_m / q6_k）。K-quant必须交给llama-quantize。

对原流程的修正：原对话中建议的python convert_hf_to_gguf.py ... --outtype q4_k_m会被argparse直接以invalid choice拒绝，不可能产出q4_k_m。该建议错误。

2 数据 训练启动 Dropped invalid example: [] 数据集格式配置与文件不匹配 核对formatting/tags，用Num examples复验
3 训练 cutoff 2048 / bs 4 CUDA out of memory. Tried to allocate 2.38 GiB ... 20.92 GiB memory in use 反向传播logits梯度峰值 降 cutoff / batch
4 训练 cutoff 2048 / bs 2 Tried to allocate 2.32 GiB ... 21.04 GiB memory in use 同上，最长样本触发 同上
5 训练 cutoff 2048 / bs 2 + gc 同 #4 单样本峰值不受gc影响 cutoff降到1024
6 训练 二次启动同目录 Output directory already exists and is not empty 安全拦截 --overwrite_output_dir True或换目录
7 量化 convert_hf_to_gguf.py can't open file '/root/llama.cpp/convert_hf_to_gguf.py' 未clone仓库 git clone ggml-org/llama.cpp
8 量化 横线文件名 can't open file '.../convert-hf-to-gguf.py' 文件名记错 以ls结果为准
9 量化 转换写词表 FileNotFoundError: ... tokenizer.model→No module named 'triton.backends'→Could not import module 'AutoTokenizer' torch/triton/transformers版本链断裂 恢复GPU torch与匹配triton

13 认知 认为ollama create会量化 无报错，但产物仍为bf16 Ollama官方明写导入时不量化 先用llama-quantize产出GGUF，再改写 Modelfile
14 认知 认为「导出量化等级」= GGUF量化 无报错 该选项实为GPTQ（none/8/4/3/2） 明确区分GPTQ与GGUF两条路线

附：本文相对原流程的三处硬修正（均有源码/官方文档依据）

1.--outtype q4_k_m不可行——convert_hf_to_gguf.py的合法值仅f32/f16/bf16/q8_0/tq1_0/tq2_0/auto。
2. LLaMA-Factory的「导出量化等级」不是GGUF——它是GPTQ位数量化，选项只有none/8/4/3/2。
3.ollama create不量化——官方原句："Ollama does not quantize GGUF models during import."
